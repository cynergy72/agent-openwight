# 튜닝 절차

## 1. 진단 순서
1. **병목 단계**: EXPLAIN 에서 예상 시간이 가장 큰 단계, DBQL 에서 CPU/IO/스풀이 큰 쿼리부터.
2. **추정 신뢰도**: 병목 단계가 `no/low confidence` 면 통계 문제부터 의심 (추정이 틀리면 나머지 판단도 틀림).
3. **조인 방식과 배치**: product join, 대용량 재분배·복제.
4. **접근 경로**: 대용량 all-rows scan, 파티션 제거 여부, 함수로 감싼 조건.
5. **데이터 양**: 스풀 행 수 × 행 길이 (불필요 컬럼, 조인 전 집계).
6. **분산**: 스큐 (DBQL CPU 스큐, 테이블 스큐, 조인 키 쏠림).
7. **설계**: PI/PPI/인덱스/데이터 타입이 쿼리 패턴과 맞는지.

## 2. 조치 등급 (권고는 반드시 등급을 붙인다)
| 등급 | 내용 | 위험 | 검증 |
|---|---|---|---|
| A. 쿼리 재작성 | SQL 만 변경 | 낮음 (결과 동일성 확인 필요) | 에이전트가 EXPLAIN 으로 즉시 비교 |
| B. 통계 | COLLECT STATISTICS | 낮음 (수집 리소스) | 수집 후 EXPLAIN 재비교 |
| C. 설계 변경 | PI, 파티션, 인덱스, 타입, 압축 | 높음 (테이블 재생성, 배치 영향) | DBA 검토·테스트 환경 검증 |

A → B → C 순으로 권고한다. C 는 반복 실행되는 핵심 쿼리이거나 A/B 로 해결되지 않을 때만.

## 3. 검증
- 같은 조건에서 EXPLAIN 전/후 비교: 총 예상 시간, product join 수, 전체 스캔 수, 신뢰도, 스풀 크기.
- 재작성은 결과가 같아야 한다: 출력 컬럼 동일, 필요하면 건수·합계 비교 쿼리로 확인.
- 예상 시간은 상대 지표. 운영 반영 후 DBQL 의 CPU/IO 로 실제 효과를 확인한다.

## 4. 리포트에 쓸 형식
각 튜닝 포인트마다: `TP-ID 이름 | 근거(EXPLAIN 단계/지표) | 조치(등급) | 기대 효과`.
